## 区块一：入口级检查

### [✅] 系统是否通过被广泛信任的协议暴露了非标准功能？

**发现**: 人人信通过 HTTP/HTTPS 暴露了 API 端点，但有一个关键的非标准机制——**f-sign 签名系统**。每个请求需要携带一个服务端验证的签名，签名算法不公开（不在前端JS中硬编码）。

**信任假设**: "只有知道 f-sign 算法的客户端才能构造有效签名"——这意味着系统信任 f-sign 作为 API 调用的身份验证和完整性保障。

**攻击面含义**: f-sign 是唯一的安全门。一旦 secret 泄露或算法可逆向，整个 API 层无防护。

**标记**: ✅ "协议入口信任边界" — HTTP 是标准协议，但 f-sign 是非标准扩展。

### [✅] 系统是否有"两个系统之间"的协议转换层？

**发现**: 人人信存在三层协议转换：
1. **Nginx 网关层**: HTTP → 内部路由（决定 405 拦截 vs 202/201 放行）
2. **JSON vs Form 路径层**: 相同端点根据 Content-Type 走不同解析路径
3. **前端JS → API 网关**: 前端负责 appKey 注入和 header 构造

**关键转换差异**: 
- Form 路径: 所有端点需要 f-sign ✅
- JSON 路径: 部分端点无 f-sign 检查，直达业务层（211响应）

**标记**: ✅ "翻译层信任边界" — JSON/Form 两条路径的拦截器配置不一致。

**攻击面含义**: JSON 路径是 f-sign 绕过后门。参数不齐全时是211（业务层错误），参数齐全时触发f-sign（201）。

### [✅] 系统有可观测的真实压力事件吗？

**发现**: 有。从测绘记录可观测到的真实事件：
- 2026-05-25: 生产前端 JS 泄露五套环境配置（appKey 硬编码）
- 2026-05-27: `registerCom` 端点死亡（从无 f-sign 到全 405）
- f-sign 算法未泄露但前端 JS 已被大规模审计
- FAT 环境与生产环境行为差异可观测

**标记**: ✅ 有可观测事件 — 平台方在发现探测后迅速加固了 registerCom

### [✅] 系统的信任链中是否存在未文档化的内部通道？

**发现**: 存在三个未文档化通道：
1. **f-sign 签名算法**: 不在任何文档中描述，不在前端JS中硬编码，仅服务端验证
2. **appKey 系统**: 所有环境 appKey 硬编码在前端，但注册/分发机制无文档
3. **198.18.0.0/22 内部子网**: 18个内部子域名 TCP 通但 HTTP 空回复 — 需要应用层 mTLS 或特定 header

**标记**: ✅ "未文档化信任通道" — f-sign 算法 + 内部子网

**攻击面含义**: 内部子网的存在说明人人信有 Kubernetes/Docker 内网。如果 SSRF 可行，内部 6379 (Redis) 可能仍然可达。

**区块一覆盖率**: 4/4 ✅ — 区块一的新增条目（未文档化通道）在本系统中找到了直接映射

## 区块二：数据层检查

### [✅] 用户输入是否被拼接进结构化格式？

**发现**: 多个端点接收 JSON body。特别关注：
- `addLoan`: `{orderId, borrowerUid, borrowerRole, lenderUid, lenderRole, amount, installmentType, borrowTime, totalPeriod, eachPeriodDays}` 
- 曾确认 `installmentType` 参数触发 f-sign 签名检查（参数齐全→201）
- 曾确认 `callbackUrl` 参数存在 SSRF 漏洞

**分隔符检查**: JSON 是结构化格式，但 `callbackUrl` 参数传递 URL 字符串（可包含 `?` `&` `#` `://` 等分隔符）直接给后端发起 HTTP 请求。

**标记**: ✅ 分隔符注入面 — callbackUrl URL 参数

### [✅] 数据是否跨越了不同系统边界？

**发现**: 数据在人人信架构中跨越多个边界：
1. 前端 JS → Nginx Gateway → Spring Boot 后端 → MySQL/MongoDB
2. SSRF 路径: callbackUrl → 服务端 HTTP 请求 → 内网服务
3. appKey: 前端 → API 请求头 → 认证中间件 → 业务逻辑

**标记**: ✅ "数据翻译边界"

### [✅] 是否存在"最后者胜"的重复键解析器？

**发现**: 已确认人人信某些端点使用 `JSON.parse()` 解析。存在"最后者胜"行为：
- 当 JSON 中有重复 key 时，最后一个值覆盖前面的
- 这在参数验证中可能被利用

**验证**: 曾在 `registerUser` 端的 `telephone` vs `idCardNo` 字段出现覆盖行为（同参数位置不同语义）。

**标记**: ✅ "覆盖注入面"

### [✅] 外部输入是否进入内部参数解析器？

**发现**: 经典案例——`callbackUrl` SSRF：
1. 进入参数流？✅ callbackUrl 作为 JSON 字段发送
2. 前缀可注入？可通过 URL scheme 控制协议（`gopher://`、`file://`、`http://`）
3. 参数有副作用？✅ 服务端发起 HTTP 请求到 callbackUrl → 可探测内网

**验证**: SSRF 已确认 — 内网 53 个端口可达，其中 `6379 OPEN Redis` 可确认。

**标记**: ✅ 参数注入三条件全满足 — callbackUrl

**区块二覆盖率**: 4/4 ✅

### [✅] 环境/调试模式的切换是否可被外部输入影响？

**发现**: 未直接确认模式切换注入，但存在环境隔离缺陷：
- **UAT 与 PROD 共享同一 appKey** — 环境隔离缺陷意味着 UAT 环境可以调用 PROD 接口
- 多套 appKey 共存于前端JS（DEV/FAT/UAT/PROD）

**标记**: ✅ "环境隔离失效" — 共享 appKey 导致 UAT/PROD 边界模糊

### [⚠️] 被检测的字符在到达检查点前是否经过转换？

**发现**: `callbackUrl` 参数在到达 SSRF 执行点前经过两次转换：
1. JSON body → Java String 解析
2. String → HTTP 客户端 URL 参数 → 服务端请求发起

**转换**: URL 中的特殊字符（`://` `?` `&` `#`）在 JSON 解析阶段保持逐字传递，但在进入 HTTP 客户端时被重新解释为 URL 组件。

**标记**: ⚠️ 存在分隔符语义转换 — `://` 从字符串字面转换为协议分隔符

**差异化**: 人人信 SSRF 中的语义转换与 CVE-2026-3854 的分号转换类似但不同——这里是**URL 结构语法**的语义转换，不是分隔符解析器的语义转换。checklist v1.1 的"解析阶段分隔符语义转换"条目涵盖此场景。✅

### [✅] 系统中的"第一印象"声明和实际运作路径之间是否有信息差？

**发现**: 明显的信息差：
1. **"注册"端点**: `registerCom` 作为用户注册入口，表面上是最低权限操作，实际上曾是**唯一无 f-sign 的 POST 端点**——注册流程不要求签名，但其他操作要求。这意味"注册是公开入口"的第一印象与实际"注册是无签名后门"有信息差。
2. **"f-sign = 安全"**: 系统设计者通过 f-sign 宣称"API 安全"，但 JSON 路径绕过说明 f-sign 不是全局强制。
3. **"HTTPS = 安全"**: 但 appKey 明文在前端JS中。

**标记**: ✅ "善意声明缺口" — registerCom 曾是最大缺口
