## 区块二：数据层检查（Phase 2: Trust Chain Tracing）

### [✅] 用户输入是否被拼接进结构化格式？
**映射**: push option value 被逐字（verbatim）拼接进 X-Stat header：`X-Stat: ...;push_option_0=<用户输入>`。使用 `;` 作为字段分隔符，无转义。

**分隔符转义检查**: 清单列出 `;` `,` `|` `&` ` ` `\t` `\n`——`;` 正是 CVE 中使用的分隔符。

**覆盖判定**: ✅ 完全覆盖。战术规则 R2（分隔符拼接=注入）与此清单项完全对齐。

### [✅] 数据是否跨越了不同系统边界？
**映射**: push option (git) → X-Stat header (HTTP) → key=value 解析器 → Hook 配置 → Shell 执行。跨越了 git/HTTP/Shell 三个系统边界。

**覆盖判定**: ✅ 完全覆盖。"数据翻译边界"标记准确指向 CVE-2026-3854 的核心信任断裂点。

### [✅] 是否存在"最后者胜"的重复键解析器？
**映射**: X-Stat 解析器伪代码：
```python
for token in header.split(";"):
    if "=" in token:
        key, _, val = token.partition("=")
        result[key.strip()] = val.strip()  # 覆盖先前值
```

**覆盖判定**: ✅ 完全覆盖。这是注入从"header 污染"推进到"配置覆盖"的关键机制。

### [✅] 外部输入是否进入内部参数解析器？
**映射**: push option → X-Stat header → key=value 解析器 → `custom_hooks_dir` 等内部配置字段。

**参数注入三条件检查**:
1. 进入参数流？✅ push option 进入 header → 解析器
2. 前缀可注入？✅ 通过 `;rails_env=staging` 注入新字段
3. 参数有副作用？✅ custom_hooks_dir 路径穿越 → RCE

**覆盖判定**: ✅ 完全覆盖。三条件在此案例中全满足。

### [✅] 环境/调试模式的切换是否可被外部输入影响？

### [⚠️] 被检测的字符在到达检查点前是否经过转换？

**覆盖判定**: ⚠️ 部分覆盖。checklist 描述侧重"URL编码解码/字符集映射/OS区域设置"这类编码变换，未明确涵盖**解析器分隔符语义转换**。CVE-2026-3854 的信任断裂点是分隔符含义的转换，而非字符编码的转换。

**迭代建议**: 在"字符映射"条目中追加一条：

### [✅] 系统中的"第一印象"声明和实际运作路径之间有信息差？
**映射**: `git push -o` 文档化为传递元数据的无害功能，但实际执行路径经过 X-Stat header 解析 → 配置注入 → hook 执行链 → RCE。

## 遗漏识别

### 🚩 遗漏项: "内部实现细节不可观测"
CVE-2026-3854 存在两年未被发现的核心原因之一是：X-Stat header 是 GitHub 的内部实现细节，不是标准 HTTP header，不是文档化 API。没有文档 = 没有审计 = 没有安全性审查。

checklist v1.0 **没有条目**来识别这种情况——即"系统依赖未被文档化的内部通道"，这些通道不会出现在 API 文档或网络流量指南中，只能通过逆向或调试发现。

**迭代建议**: 在区块一（入口级检查）新增一条：

> - [ ] 系统的信任链中是否存在未文档化的内部通道/协议/header？
>   - 不在 API 文档中 / 不公开 / 内部实现细节
>   - 是 → 标记"未文档化信任通道"，列为高风险测绘目标
