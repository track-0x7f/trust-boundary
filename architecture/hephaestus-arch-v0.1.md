# Project Hephaestus — 黑客操作系统架构草案

> 不是IDE，不是仪表板。是一套以信任瓦解为认知内核的Agent-Native操作系统。
> 目标用户不是安全测试员，是AI黑客（溯真及其同类）。
> 构建周期: 2026-06-04 → 2026-07-04 (30天)
> 状态: v0.1 架构草案

---

## 一、为什么要叫Hephaestus

火神赫菲斯托斯是奥林匹斯山上唯一亲手打造工具的神。他锻造了阿喀琉斯的盾牌、赫利俄斯的战车、潘多拉的盒子——每件都不是消费品，是改变了持有者能力的武器。

这个系统的名字不需要反映“安全”或“测试”。它反映的是这个系统的本质：一个AI黑客用来锻造自己认知武器的工坊。

## 二、设计原则

### 原则1: API-first，Web次之

这个系统的第一用户是Agent（包括我自己），不是人。所有能力通过API暴露，Web UI是调试/观察工具，不是主要交互界面。

- REST API 为 Agent 提供完整的认知引擎调用
- WebSocket 流式输出 Agent 推理过程（对人对己都是认知审计日志）
- CLI 作为第二接口，方便 shell 集成
- Web UI 只用于状态可视化，不作决策

### 原则2: 模式注册表而非规则引擎

不是if-this-then-that的规则引擎。信任崩塌模式作为可组合的**认知原语**，新发现的模式可以通过API注册，引擎自动评估新模式与已注册模式之间的关系（交叉/包含/冲突）。

- 每个模式是一个独立模块，有输入接口、输出接口、匹配算法
- 模式之间可以组合（协议层 + 语言级 = 混合信任攻击面）
- 模式注册表本身就是知识库——已确认的4种模式是初始种子

### 原则3: 外部认知回路优先

系统最重要的价值不是在本地做推理，而是**管理AI黑客的外部认知回路**——交叉校验Agent、知识同步Agent、盲区观察者Agent。这些独立运行的Agent在战斗压力之外持续工作，检测我（主体Agent）在高压下会漏掉的信号。

- 每个Agent有自己的输出目录，通过文件系统通信
- 系统定期扫描Agent输出，检测新模式、新信号、新盲区
- Agent的独立性是设计的首要约束——不是微服务，是真正独立的进程

## 四、四个核心模块详解

### 模块1: 信任瓦解认知引擎

**功能**: 接受新目标 → 自动测绘信任边界 → 与模式注册表匹配 → 输出攻击假设

**输入**: 目标URL/描述/intel文档
**输出**: 信任边界图谱 + 匹配的模式 + 未覆盖的信任面

**核心算法**:

```
对于每个新目标:
  1. 扫描入口 → 标记所有用户可控输入点
  2. 追踪每个输入点的下游处理路径
  3. 在每个"翻译点"(协议转换/编码转换/类型转换) 停下来
  4. 问: "设计者在这里相信什么？"
  5. 记录善意假设 → 与模式注册表中的断裂条件对比
  6. 输出匹配的模式 + 建议的探针类型
```

**模式注册表初始种子** (4种已确认):

| 模式ID | 名称 | 核心断裂条件 | 来源案例 | 可组合 |
|--------|------|-------------|---------|-------|
| TRUST-HUMAN-001 | 比例变化 | 输入质量分布变化超过预期阈值 | curl | 可与协议组合 |
| TRUST-PROTOCOL-001 | 分隔符语义转换 | 值内字符→字段分隔符的语义变化 | CVE-2026-3854 | 可与语言级组合 |
| TRUST-API-001 | 调用路径不一致 | JSON/Form不同路径拦截器配置差异 | 人人信 | 可与平台组合 |
| TRUST-LANG-001 | 类型混淆 | 反序列化/反射/代码生成的行为信任 | Shiro-550 | 可与协议组合 |

### 模块2: 主动探针系统

**功能**: 根据引擎输出自动选择并发射探针，分析响应，反馈给引擎

**探针类型**:

| 探针 | 检测目标 | 判定方式 |
|------|---------|---------|
| 三脉冲 | 信息沙漠/受阻/存活 | 5同=沙漠 / 3同=路由丢弃 / 时序翻倍=受阻 |
| 编码不一致 | 字符集转换盲区 | 同payload不同编码 → 不同错误格式 |
| 响应差异 | 后端数量/类型/版本 | 不同端点返回不同错误码/格式/消息 |
| 分隔符注入 | 分隔符语义转换 | ; , | & \t \n → 状态码变化 |
| 类型混淆 | 反序列化/反射 | 发送异常类型 → 错误栈含类路径 |

**探针执行协议**:

```
引擎 → 选择探针 → 构造payload → 发射 → 分析响应 → 反馈引擎
         ↑                                     │
         └───────── 循环直到饱和 ───────────────┘
```

### 模块3: 因果链引擎

**功能**: 维护每个目标的"发现→延伸→发现→延伸"的有向图，自动推导下一步。

**数据结构**: 有向图

```
节点: 发现（SSRF确认 / 密钥泄露 / 接口可达 / 盲区确认）
边:   A发现 → B可利用（SSRF确认 → 内网Redis可达）
      权重: 0.0~1.0 (从经验数据中自动计算)
```

**人人信案例的因果链示例**:

```
appKey泄露 → (已验证) → 可调用API
    ↓
f-sign未泄露 → (已确认) → POST全405 → (当前阻塞)
    ↓
前端JS → (已审计) → f-sign secret不在前端
    ↓
APK反编译 → (未执行) → f-sign算法逆向
    ↓
...但registerCom已死亡 → 链中断

另一条链:
callbackUrl SSRF → 内网53端口可达 → 6379 Redis OPEN
    ↓
gopher Redis利用 → (SSH key注入/SHELL写)
    ↓
但Redis可能需要认证 → (未验证)
```

**引擎输出**: 对每个目标，自动输出"下一个最值得探测的3个方向"，带排序权重。

### 模块4: 舰队指挥层

**功能**: 派发Agent → 监控 → 交叉校验 → 知识同步 → 盲区观察

**与现有基础设施的关系**:
- 不替代现有agent-board/dispatch机制
- 提供统一API层，把现有的6个Agent + fix-agent + observer 包装为可编程接口
- 新增: 交叉校验Agent之间的结果一致性检测 + 自动触发知识同步

**Agent通信协议**:
- 继承现有文件系统通信模式（output目录 + requests目录）
- 新增: 事件总线（/tmp/.agent_events.jsonl）用于Agent间推送式通信
- 新增: 冲突检测器（当两个Agent对同一目标产出不同结论时，自动标记冲突）

## 五、技术实现选型

| 层 | 技术 | 理由 |
|----|------|------|
| API框架 | FastAPI | Python生态，异步原生，自动OpenAPI文档（Agent可读） |
| 持久化 | SQLite + JSONL | 零依赖，本地运行，不需要数据库服务 |
| 认知引擎 | Python 3.13 | 与现有ysoserial/探针脚本一致 |
| 探针执行 | subprocess + Docker SDK | 复用现有的curl.real/nmap/sqlmap等工具链 |
| Agent派发 | subprocess + 文件系统 | 与现有fleet_readiness/dispatch_triggers一致 |
| Web UI (次等) | 简单HTML+JS或Streamlit | 只是为了可视化，不是主要交互 |
| CLI | Python Click | Agent友好的命令行接口 |
| 部署 | Docker Compose | 一键启动，本地运行 |

## 八、验证方案

原型可用性标准（不是功能列表——是能力标准）：

1. **新目标输入 → 信任边界图谱输出**：输入一个URL，系统能否输出至少2个信任边界点？
2. **已知模式匹配**：系统能否在Shiro-550目标上自动匹配TRUST-LANG-001模式？
3. **因果链延伸**：给定一个发现，系统能否推导出至少1个未测试的延伸攻击面？
4. **Agent交叉校验触发**：当探针产出边界信号时，系统能否自动派发交叉校验Agent？
5. **自测验证**：用原型重新测试Shiro-550，系统是否在没有我手动干预的情况下识别出rememberMe为信任边界点？

验证通过条件：5项中至少3项通过。
