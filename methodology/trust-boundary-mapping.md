# 信任边界测绘方法论

如何测绘复杂系统中信任如何被设计、如何被传递、以及在哪里断裂的。

## 为什么需要这份手册

信任边界测绘不是安全审计，不是漏洞扫描。它回答的是另一个问题：**当善意设计在意外场景中失效时，系统发生了什么？**

我在四个系统（灰石社区、星环贸易站、CrowdWorks 客服漏斗、curl 漏洞披露流程）中重复了同一套测绘方法。这份手册就是把那四轮经验提炼成可复用操作步骤的产物。

---

## 方法论概述

信任边界测绘由四个阶段组成。每个阶段依赖前一个的输出。

```
阶段一：系统选择     → 阶段二：信任链追踪     → 阶段三：边界识别     → 阶段四：压力测绘
  选择目标系统         绘制信任关系清单         识别结构脆弱点          用真实事件测试边界
  定义边界范围         标注担保形式             定位善意假设            记录维持/断裂/修复
  识别参与者          评估可验证性             定义边界条件            得出结论
```

---

## 阶段一：系统选择

### 1.1 选择标准

信任测绘的目标不是"最有趣"或"最脆弱"的系统——是**信任架构清晰可观测**的系统。选择时问三个问题：

1. **这个系统里显然有信任在传递**——有人需要相信另一个人或另一个组件会按预期行事。如果系统完全不需要信任（例如纯数学算法），它不是测绘的好目标。
2. **信任的边界可以被外界观测**——系统不对公众开放内部信任规则也没关系；只要信任关系的输入和输出可观测（例如：政策文档描述了流程，历史记录显示了行为），测绘就是可能的。
3. **这个系统在不同场景中被测试过**——有历史事件、争议、公开讨论的记录。纯理论设计没有测绘价值；被真实压力测试过的系统才有。

### 1.2 边界定义

明确测绘的范围。一个系统的信任架构通常是多层的，你可能只测绘其中的一个子集。

**边界声明示例**（来自 curl 案例）：

> 测绘范围：curl 项目的安全漏洞披露流程。从发现者提交报告到公开披露的完整信任链。不包括：curl 内部的代码审查信任、社区治理信任、TLS 证书信任——除非它们与披露流程直接相交。

### 1.3 参与者识别

列出系统中所有信任关系的参与方。每个参与者可能有多个角色。

常见参与方类型：
- **信任方**——需要信赖某事或某人
- **被信任方**——被期待按某种方式行事
- **担保者**——为被信任方提供信用背书
- **中介/平台**——承载信任关系的通道
- **审计者**——验证信任是否按设计执行的第三方

## 阶段二：信任链追踪

### 2.1 信任关系清单

对系统中每一条信任关系，记录以下信息：

| 字段 | 含义 | 示例 |
|------|------|------|
| 编号 | T1, T2, ... | T1 |
| 信任方 | 谁在信任 | 发现者（漏洞提交者） |
| 被信任方 | 信任谁 | 安全团队 |
| 信任内容 | 相信什么 | 相信团队会公正评估报告 |
| 担保形式 | 如何保证 | 声誉/历史记录 |
| 可验证性 | 信任是否可被检验 | 弱——团队组成不透明 |

### 2.2 担保形式的可验证性分级

可验证性评估是信任链测绘的核心输出。它告诉你在哪里信任是可见的、可检验的——以及在什么是隐式的、只能依赖善意假设的。

| 等级 | 定义 | 示例 |
|------|------|------|
| **强** | 被信任方无法偏离而不被发现 | 公开的 commit 历史、可验证的签名 |
| **中** | 偏离可被检测但需要主动审计 | 安全公告的可审阅性、发布流程的可追溯性 |
| **弱** | 偏离几乎无法被信任方发现 | 不透明的团队组成、无公众名单 |
| **隐式** | 完全依赖善意假设，无任何验证机制 | 信赖合约另一方会公平行事 |

### 2.3 绘制信任流

用一个简单的有向图表示信任关系的流向。箭头从信任方指向被信任方。

```
发现者 → [HackerOne] → 安全团队(私密列表) → Daniel(最终决策)
                                 ↕
                            distros@openwall
                                 ↕
                            CVE分配 → 修复 → 公告
```

标注每条边上的担保形式和可验证性等级。

## 阶段三：边界识别

这一阶段从"描述系统"切换到"定位脆弱点"。目标是找到善意设计在意外场景中的失效缺口。

### 3.1 善意假设定位

对每一条信任关系，问这个问题：

> **系统设计者假设了什么才让这条信任关系成立？**

这个假设通常是善意的——但正因为是善意的，它往往没有被显式记录下来。

**示例**（curl 案例 T5）：
- 信任关系：发现者 → 系统（经济激励）
- 善意假设：发现者读到"no bug bounty"后会理解这是指项目不付钱（而非完全没有赏金）
- 为什么是善意的：Daniel 只是想诚实地告诉发现者别为了钱来报告
- 边界条件：新发现者读后放弃报告，而有经验的发现者知道实际上有 IBB 赏金

### 3.2 重复模式清单

以下模式在多个系统中反复出现。它们不是 bug——是善意设计在特定条件下的结构化表现。

#### 模式 A：善意声明缺口

一句诚实但位置关键的声明，在接收端翻译成了系统设计者未曾预期的含义。

**识别特征**：政策/声明是技术上真实的，但发生在用户决策链的关键入口处，在用户还不了解系统实际运作方式时定义了预期。

**已知案例**：
- curl："No bug bounty" → 新发现者被劝退 / 实际有 $480–$4,660 赏金
- CrowdWorks："よくある質問をご確認ください" → 7 层漏斗后才有客服入口

**测绘方法**：找到系统中"第一印象"声明（政策文档首页、FAQ 入口、注册页的条款），然后追踪实际运作路径，比较两者之间的信息差。

#### 模式 B：单点疲劳

信任集中在单一个体或小组件上时，系统的弹性取决于那个点的个人极限，而非系统设计的极限。

**识别特征**：信任链中有一个节点承担了不成比例的责任——其不可用或错误行为会影响整条信任链。

**已知案例**：
- curl：Daniel 是唯一决策者，7 人团队的总时间预算决定披露效率
- 人人信（灰石）：马克被透支后系统失去担保功能
- 星环：布雷肯用封存维持信任链，无备份

**测绘方法**：检查每条信任链上的决策节点是否有冗余、文档化替代路径、或负载监测机制。如果单点不可用或达到个人极限，流程是否可继续？

#### 模式 C：比例变化脆弱性

系统在稳态设计时没给变量留余量。当输入的比例变化时（不是数量，是比例），信任链在不变的人力资源下开始疲劳。

**识别特征**：系统的设计能处理数量的波动，但处理不了组成结构的变化。

**已知案例**：
- curl：报告数量从 ~2/周增长到 3–4/周（翻倍），但 AI slop 占比从 ~0% 涨到 ~20%，有效报告率降至 5%。团队人力不变。
- CrowdWorks：不是用户数量增加，是"需要人工客服的用户比例"因为 FAQ 迭代而相对变化。

**测绘方法**：检查系统是否假设输入的质量分布是恒定的。如果是，当质量分布变化时，系统的哪个部分先达到极限（时间预算、注意力、情绪耐力）？

### 3.3 边界条件描述

对每个善意假设，定义使其失效的边界条件：

| 要素 | 描述 |
|------|------|
| 善意假设 | 设计者假设了什么 |
| 意外场景 | 什么条件下这个假设不成立 |
| 失效模式 | 假设不成立时信任关系如何变化 |
| 影响 | 谁承担损失，损失是什么 |

## 阶段四：压力测绘

信任链在正常态下的行为只能告诉你"系统应该怎么运作"。压力测绘告诉你"当系统被挑战时，信任关系如何维持、断裂、或自我修复"。

### 4.1 选择压力事件

寻找系统中发生过或正在发生的真实压力事件。理想的事件是：

1. **有公开记录**——邮件列表、博客、声明、讨论串
2. **测试了明确的信任关系**——不是技术故障，是信任决策被质疑
3. **有可观察的结果**——信任关系维持了、断裂了、还是被修复了

### 4.2 事件测绘模板

对每个事件记录：

```
事件名称：[简要描述]
时间：[日期或时间段]
压力类型：[单次争议 / 系统性压力 / 信任退化 / 主动改进]

被测试的信任关系：[T1, T2, ... 引用阶段二的编号]

压力触发：[发生了什么？]

信任链反应：
[信任关系] → [反应] → [状态（维持/断裂/改善）]

结束状态：[事件结束后信任链是否恢复？是否留下永久变化？]

测绘笔记：
[该事件揭示了你之前在正常态测绘中没有看到的什么？]
```

### 4.3 压力类型

| 类型 | 特征 | 恢复方式 |
|------|------|---------|
| 单次争议 | 明确的分歧事件，有人挑战了决策 | 通常可恢复，可能留下永久排除或流程改进 |
| 系统性压力 | 持续积累的低质量输入 | 不会单次恢复，需要结构性调整 |
| 信任退化 | 信噪比缓慢下降，善意被消耗 | 最难恢复，因为损失不是单次事件造成的 |
| 主动改进 | 没有压力，但系统自动提升了透明度 | 永久改善，说明系统具备自适应改进能力 |

---

## 测绘输出规范

信任边界测绘的产出不是"发现了漏洞"——是"画出了信任边界线"。一份完整的测绘产出应包含：

1. **信任链追踪图**——谁信任谁，担保形式，可验证性分级
2. **善意假设清单**——每个设计选择的底层假设
3. **结构脆弱点**——善意声明缺口 / 单点疲劳 / 比例变化脆弱性（按模式分类）
4. **压力测试记录**——真实事件下信任链的行为
5. **修复提案（可选）**——不修补技术漏洞，修补信任传递的流程设计

## 附录A：战术规则回灌 — 从CVE-2024-4577到方法论的4条回灌

> 来源：CVE-2024-4577（PHP CGI 参数注入 — Orange Tsai / DEVCORE）
> 来源文件：`research/CVE-2024-4577-analysis.md`
> 回灌时间：2026-06-03
> 回灌人：溯真
>
> 以下4条规则不是单独的攻击技巧——它们是从单一标本中剥离出的结构属性，
> 被反哺到信任边界测绘的方法论各阶段中。每条规则对应一个阶段，
> 说明攻击战术如何丰富了信任测绘的可操作维度。

---

### 规则R1：系统间翻译错误是富矿

**原始表述**：
> 当数据跨越两个系统的边界时（URL→命令行、编码A→编码B、API→内部函数），
> 检查转换后的数据是否与转换前保持语义一致。
> 翻译错误是攻击者与防御者之间最不对称的战场。

**对应阶段**：阶段三 — 边界识别（3.1 善意假设定位）

**回灌价值**：
原始方法论在3.1节只关注"设计者假设了什么才让信任关系成立"——这是一个静态分析问题。
R1增加了**动态边界探测维度**：两个系统之间的数据翻译本身就是一个潜在断裂点。

**具体补充到方法论的三个操作点**：
1. **翻译一致性检测**：在善意假设清单中，对每条涉及跨系统数据交换的信任关系，
   附加"数据在A系统和B系统的表示是否一致"的检查项。
2. **翻译路径测绘**：在每个信任链追踪的末端，标注数据是否跨越了不同的解析器/编码器/协议转换器。
3. **"谁先处理"问题**：对每次数据转换，问"这个字符串到底先被哪个处理器看到？
   那个处理器在它看到之前做了什么？"——这是Orange Tsai在CVE-2024-4577中的核心思维跳板，
   可直接转化为测绘阶段三的标准化探测问题。

**案例连接**：curl案例的P1发现（"No bug bounty" → IBB赏金）在结构上与CVE-2024-4577同构——
声明（数据）跨越了"编写者意图"和"新读者理解"两个系统，翻译产生了预期之外的语义。

---

### 规则R2：修复视线盲区检查

**原始表述**：
> 如果一个修复通过检测特定字符来阻止注入，检查这个字符在到达检测点之前
> 是否经过了任何可能改变它的转换。修复只在一个系统上下文中安全；
> 跨系统的转换链可能创造出修复未考虑的变体。

**对应阶段**：阶段三 — 边界识别（3.3 边界条件描述）

**回灌价值**：
原始方法论3.3节定义了善意假设失效的边界条件（意外场景、失效模式、影响）。
R2将"修复是否假设了某字符在整个处理链中保持身份不变"引入为边界条件的一个子类型。

**具体补充**：
在"边界条件描述"模板中增加一个字段：
```
修复视线盲区：被检测的字符（如 `-`）在到达检测点前是否经过转换？
  - URL编码/解码链？
  - 字符集映射（Best-Fit、ICU、iconv）？
  - OS/区域设置差异？
```
这个字段将R2从"漏洞特征"提升为"可复用的测绘检查项"。

---

### 规则R3：参数注入面的三个必要条件

**原始表述**：
> 任何参数注入漏洞需要三个条件同时满足：
> 1. 外部输入进入内部参数流
> 2. 参数前缀字符可注入
> 3. 参数有副作用

**对应阶段**：阶段二 — 信任链追踪（2.1 信任关系清单）

**回灌价值**：
原始方法论2.1节关注"谁信任谁、担保形式、可验证性"。
R3增加了一个技术信任维度的检查：**数据是否从外部输入直接流入了内部参数解析器？**

**具体补充**：
在信任关系清单中增加可选字段：
```
数据流路径：外部输入 → [步骤1] → [步骤2] → ... → 内部执行点
参数注入三条件：
  - 条件1（进入参数流）：是/否
  - 条件2（前缀可注入）：是/否/不适用
  - 条件3（参数有副作用）：是/否
全面满足？是 → 高优先级信任边界
```
这不是替换信任链追踪——是在信任关系可能转化为技术漏洞时提供早期预警信号。

---

### 规则R4：CGI接口本身是一个信任边界

**原始表述**：
> CGI协议的设计假设Web服务器和应用程序在同一个信任域中。
> 任何使用CGI/FastCGI模式的系统都应该审查接口两端的编码假设。

**对应阶段**：阶段一 — 系统选择（1.1 选择标准 + 1.2 边界定义）

**回灌价值**：
原始方法论1.1节的选择标准为：信任架构清晰可观测、边界可外界观测、有真实压力测试记录。
R4新增了一个明确的**候选系统类型**：CGI/FastCGI/WSGI接口——因为它们天然包含
"两个系统之间有一个协议转换层"，这个转换层的编码假设是动态边界探测的理想标本。

**具体补充**：
在"参与者识别"（1.3节）中增加一个候选参与者类型：
```
协议中介：位于两个系统之间的协议转换器（如FastCGI模块/gRPC网关/API网关），
其编码假设是信任边界测绘的高价值切入点。
```

## 附录B：战术规则回灌 — 从CVE-2026-3854到方法论的5条回灌

> 来源：CVE-2026-3854（GitHub RCE via X-Stat Push Option Injection — Wiz Research）
> 来源文件：`research/CVE-2026-3854-analysis.md`
> 回灌时间：2026-06-03
> 回灌人：溯真
>
> 以下5条规则源自同一个漏洞链——Git Push Option 通过 X-Stat header 注入实现 RCE。
> 与附录A（编码级翻译错误）不同，附录B的规则聚焦于**协议层的信任传递错误**——
> 系统设计者相信协议功能的执行路径是安全的，因为输入经过了身份验证。
> 但这个信任假设只覆盖了入口，没有覆盖下游处理链。

---

### 规则R1：协议功能不是安全边界（CVE-2026-3854 · R1）

**原始表述**：
> git push option、HTTP header、DNS TXT record 等协议功能是合法且必需的。
> 但它们的下游处理路径通常没有受到与显式安全边界同等的审查。

**对应阶段**：阶段一 — 系统选择（1.1 选择标准）+
阶段三 — 边界识别（3.1 善意假设定位）

**回灌价值**：
原始方法论在系统选择阶段问“这个系统里有信任在传递吗”。R1补充了一个新的候选类型：

> **当系统通过一个被广泛信任的协议（git/HTTP/DNS）暴露了一个功能入口点时，
> 这个入口点本身就是一个高价值的信任边界测绘目标。**

不是因为它不安全——是因为它被信任。协议功能的信任假设是隐式的，没有被显式文档化。

**具体补充到方法论的三个操作点**：
1. **协议入口检查**：在阶段一系统选择时，额外问“系统是否通过某种协议暴露了非标准的执行路径？”
2. **信任链扩展**：在阶段二信任链追踪中，对每个通过协议功能传递的数据路径，追踪到执行终点（不停止在协议边界）
3. **隐式信任标注**：在阶段三善意假设清单中，对协议功能的每条使用路径标注“该路径的信任假设未显式文档化”

### 规则R2：分隔符拼接即是注入面（CVE-2026-3854 · R2）

**原始表述**：
> 任何将用户输入与结构分隔符（`;` `,` `|` `&` ` ` `\t` `\n`）拼接的操作都是注入点。

**对应阶段**：阶段三 — 边界识别（3.1 善意假设定位）

**回灌价值**：
原始方法论3.1节定位善意假设时问“设计者假设了什么才让信任关系成立”。
R2将这个问题转化为一个可执行的代码级检查：

> **设计者是否假设了用户输入中不会包含分隔符？**

这个假设在大部分场景下是合理的（用户确实不会主动输入分号/管道）。
但在拼接场景中，这个假设就是信任边界——系统信任用户输入不会破坏其结构。

**具体补充**：
在善意假设清单的“意外场景”一列中，增加一个固定检查项：
```
意外场景（分隔符注入）：用户输入中包含系统内部使用的结构分隔符
```
当一条信任关系涉及用户输入与结构化数据拼接时，这个检查项自动标记为“可能”，
否则标记为“不适用”。

### 规则R3：“最后者胜”解析器是覆盖攻击面（CVE-2026-3854 · R3）

**原始表述**：
> 当解析器对重复键取“最后出现”时，攻击者可以通过在序列末尾注入新键值
> 来覆盖前面设置的安全关键字段。

**对应阶段**：阶段三 — 边界识别（3.3 边界条件描述）

**回灌价值**：
原始方法论3.3节定义了“边界条件”——善意假设在什么场景下失效。
R3揭示了一种新的边界条件类别：**重复键覆盖**。

**具体补充**：
在边界条件描述模板中增加一个子类型：
```
重复键覆盖条件：
  - 系统是否将用户输入拼接进了一个 key=value 格式的序列中？
  - 解析器对重复 key 取最后出现还是首次出现？
  - 如果是“最后者胜”，攻击者是否能在序列的后端注入新键值？
```
这个子类型特别适用于测绘那些“用户输入通过拼接进入内部配置格式”的系统。

### 规则R4：环境模式差异是攻击杠杆（CVE-2026-3854 · R4）

**原始表述**：
> staging/debug/development 模式通常移除安全限制（sandbox、认证检查、速率限制）。
> 当这些模式通过可注入的配置字段切换时，它们就是攻击链中的一个杠杆点。

**对应阶段**：阶段三 — 边界识别（3.1 善意假设定位）

**回灌价值**：
原始方法论在定位善意假设时关注“功能设计”，但“非功能设计”（环境模式、日志级别、调试开关）
通常不被视为信任关系的一部分。R4将它们纳入测绘范围：

> **环境模式的切换路径本身就是一条信任边界。**

"rails_env"参数的值从被信任方（系统内部配置）切换到攻击者控制的可能性，
就是信任关系在非功能维度上的断裂点。

**具体补充**：
在阶段三的善意假设清单中增加一个标准提问：
```
环境模式假设：设计者假设了环境模式不会被外部输入影响
  - 意外场景：用户输入可以通过参数/header/配置的方式切换模式
  - 失效模式：安全限制在非预期的模式下被绕过
  - 测绘方法：列出所有可以通过外部输入切换的内部模式
```

### 规则R5：Hook/Plugin执行链是RCE引擎（CVE-2026-3854 · R5）

**原始表述**：
> 任何支持 hook/plugin/extension 的系统，如果 hook 路径可被攻击者控制，
> 就是 RCE 引擎。

**对应阶段**：阶段四 — 压力测绘（4.1 选择压力事件）

**回灌价值**：
原始方法论4.1节选择压力事件的标准是“测试了明确的信任关系，有可观察的结果”。
R5增加了一个候选压力事件类型：**hook/plugin 执行链测试**。

**具体补充**：
```
压力事件类型：Hook 执行链信任测试
  - 测绘对象：任何支持 hook/plugin/extension 的系统
  - 测绘方法：
    1. 识别所有 hook 触发点（pre-receive、post-commit、pre-push 等）
    2. 追踪 hook 路径配置的来源（硬编码/用户可控/文件系统）
    3. 检查 hook 路径是否经过路径穿越验证
    4. 检查是否有多步 hook 链（hook → 调用外部脚本 → 加载配置）
  - 信任假设：系统信任 hook 路径指向的是它预期的脚本
  - 意外场景：hook 路径被覆盖为攻击者控制的文件
```
