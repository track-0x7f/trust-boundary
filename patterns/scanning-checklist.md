# 信任边界扫描清单

> 不是方法论——是上战场前30秒扫一眼的检查表。
> 方法论告诉你"怎么做"，这份清单告诉你"该看哪里"。

## 一、入口级检查（阶段一：系统选择）

- [ ] 系统是否通过一个被广泛信任的协议暴露了非标准功能？
  - git push option / HTTP header 扩展 / DNS TXT / API 扩展字段
  - 发现 → 标记为"协议入口信任边界"
- [ ] 系统是否有一个在"两个系统之间"的协议转换层？
  - CGI/FastCGI/WSGI / gRPC gateway / API gateway
  - 发现 → 标记为"翻译层信任边界"
- [ ] 这个系统有可观测的真实压力事件吗？
  - 公开争议 / 安全公告 / 邮件列表讨论 / 博客回应
  - 无 → 标记为"有风险但测绘成本高"
- [ ] 系统的信任链中是否存在未文档化的内部通道/协议/header？
  - 不在API文档中 / 不公开 / 仅内部实现细节
  - 是 → 标记为"未文档化信任通道"，列为高风险测绘目标
  - *来源: CVE-2026-3854 — X-Stat是内部header, 无文档可审计→两年未被发现*

## 二、数据层检查（阶段二：信任链追踪）

- [ ] 用户输入是否被拼接进结构化格式？
  - header / query string / 配置键值 / JSON body
  - 是 → 检查分隔符转义：`;` `,` `|` `&` `空格` `\t` `\n`
- [ ] 数据是否跨越了不同的系统边界？
  - URL→命令行 / 编码A→编码B / API→内部函数 / HTTP header→配置文件
  - 是 → 标注"数据翻译边界"，追踪转换前后的语义是否一致
- [ ] 是否存在"最后者胜"的重复键解析器？
  - 任何 `key=value` 序列中后出现的覆盖先出现的
  - 是 → 标注"覆盖注入面"，检查序列尾部是否可被外部输入控制
- [ ] 外部输入是否进入了内部参数解析器？
  - query string → 命令行参数 / body → ini 配置 / header → hook 目录
  - 是 → 检查参数注入三条件：进入参数流？前缀可注入？参数有副作用？

## 三、信任假设检查（阶段三：边界识别）

- [ ] 设计者假设了什么才让这条信任关系成立？
  - "用户不会修改这个参数" / "值永远是数字/布尔/合法值" / "输入中不会包含分隔符"
  - 记录每一条善意假设（它们是信任边界的锚点）
- [ ] 环境/调试模式的切换是否可被外部输入影响？
  - rails_env / DEBUG=true / --dev / ?env=staging
  - 是 → 标记"模式切换攻击面"
- [ ] 被检测的字符在到达检查点前是否经过转换？
  - URL 编码/解码 / 字符集映射 / OS 区域设置 / **解析阶段分隔符语义转换**
  - 是 → 标记"修复视线盲区"，检查转换后的字符是否与检查目标一致
  - *v1.1新增*: 输入中的分隔符字符在解析阶段是否被转换了语义（值内字符→字段分隔符）？
- [ ] 系统中的"第一印象"声明和实际运作路径之间是否有信息差？
  - 政策首页 / FAQ 入口 / 注册页条款 vs 实际流程
  - 有差异 → 标记"善意声明缺口"

## 四、执行链检查（阶段四：压力测绘）

- [ ] 系统支持 hook/plugin/extension 吗？
  - 是 → 追踪 hook 路径配置来源：硬编码 / 用户可控 / 文件系统
  - 检查路径穿越验证是否完整
- [ ] 信任关系中有没有单点疲劳风险的节点？
  - 单一个体/组件承担不成比例的责任 / 无备份 / 无负载监测
  - **安全单点**: 某个组件同时负责解析和执行关键安全检查，且没有第二层验证？
  - 是 → 标记"单点疲劳脆弱性"
  - *来源: CVE-2026-3854 — X-Stat解析器是唯一防护层，无纵深*
- [ ] 系统的输入质量分布是否可能变化？
  - 有效报告率下降 / AI 生成内容占比上升 / 攻击复杂度不均
  - 是 → 标记"比例变化脆弱性"

## 五、语言级信任检查（阶段五：类型系统信任）

> 来源: Shiro-550 (CVE-2016-4437) 反序列化RCE — 第四案例，2026-06-04
> 信任模式: 语言/类型系统级信任，与前四个阶段在结构上不同

前三阶段的信任假设关心的是"设计者相信什么"，而这个阶段关心的是**"语言本身相信什么"**。Java/C#/PHP/Python 等语言的类型系统在反序列化、反射调用、代码生成时做出隐式信任决定——这些决定不受设计者控制，但可以被设计者的代码触发。

### 三层信任假设结构

每个语言级信任边界都可以拆解为三层，层次越低越根本：

```
第一层: JVM/运行时信任classpath上的所有类都是"安全的"
  → 语言设计假设: 类路径上的类只会被用于预期的目的
  → 断裂条件: 存在一条从序列化数据到任意方法调用的gadget链
  → 测绘方法: 列出目标classpath上所有实现Serializable且有readObject/get/transform等方法的类
  → Shiro-550示例: commons-collections-3.2.1.jar 中的 LazyMap/TiedMapEntry

第二层: 框架信任自己的加密/签名机制
  → 设计者假设: "我的加密/签名保护了数据的机密性和完整性"→"解密后的数据是安全的"
  → 断裂条件: 加密/签名保证了传输安全，但不保证解密/验证后的数据的行为安全
  → 测绘方法: 追踪加密边界→解密边界→使用边界的完整信任链
  → Shiro-550示例: Shiro信任"AES解密通过=数据安全"，忽略了反序列化后的行为

第三层: 信任的级联转移——下层信任不正确传递给上层
  → 设计者假设: "AES通过→数据有效→类型正确→方法安全" 自动成立
  → 断裂条件: 每个箭头都是独立的信任假设，不是自动传递的
  → 测绘方法: 对每个"信任转移箭头"单独提问——"这一步的保护目标是什么？下一步的保护目标是什么？它们相同吗？"
  → Shiro-550示例: AES保证完整性 ≠ 反序列化保证行为安全性——两个不同的安全属性被当作同一个
```

### 检查项

- [ ] 系统是否信任反序列化/类型转换/代码生成后的数据的行为安全性？
  - ObjectInputStream.readObject() / XStream.fromXML() / FastJson.parseObject() / Jackson deserialization
  - unsafe.getObject() / MethodHandle.invoke() / 反射调用类方法
  - eval() / exec() 执行代码字符串
  - 是 → 检查"三层信任假设"是否全部通过审计
  - *核心问题: "数据的行为是否在预期内" 而非 "数据是否被篡改"*
- [ ] 加密/签名的保护目标与使用场景的保护目标是否一致？
  - 示例: AES保证"传输中未被修改" vs 反序列化需要"类型行为安全"——两个不同属性
  - 不一致 → 标记"信任级联断裂"，追踪断层所在位置
- [ ] classpath/dependency树上是否存在已知gadget链？
  - commons-collections / commons-beanutils / fastjson / jackson / c3p0 / spring / log4j
  - 是 → 标记"可用gadget触发面"，优先测绘可到达的classpath
- [ ] 用户可控数据是否能够影响反序列化/反射/代码生成的目标类或方法名？
  - 序列化数据 → 目标类名 (Java full class name in stream)
  - 反射调用 → 方法名字符串
  - 代码生成 → 注入代码片段
  - 是 → 标记"类型注入面"，直接可触发RCE

## 六、验证步骤

测绘完成后，对每个标记的信任边界执行：

- [ ] 这个边界的善意假设是否被真实事件测试过？
  - 有测试 → 检查假设在事件中是否成立
  - 无测试 → 标记为"未验证的信任边界"
- [ ] 能否构造一个不依赖技术漏洞的场景来测试这个边界？
  - 发送不可预期但合法的输入 / 改变输入的位置/时序/比例
  - 不能 → 标记为"需技术手段测试"
- [ ] 测绘结果是否标注了数据源限制？
  - 哪些数据来自公开文档 / 哪些来自观察 / 哪些是推断
  - 不完整 → 标注后补

### 使用提示

这份清单不是线性执行的。根据新系统的特征跳转到对应区块：

| 系统特征 | 优先检查区块 |
|---------|------------|
| 有协议扩展功能 | 区块一 + 区块二 |
| 有编码/协议转换层 | 区块一 + 区块三 |
| 有用户输入拼接 | 区块二 + 区块三 |
| 有 hook/plugin 机制 | 区块四 |
| 有反序列化/反射/代码生成 | **区块五**（新增，独立于前四阶段） |
| 完全未知的新系统 | 区块一 → 二 → 三 → 四 → 六 全链跑一遍 |

> 区块五（语言级信任）独立于其他区块——即使系统没有外部接口，语言级信任边界仍然存在。classpath本身就是一个攻击面。
