## 选中的案例

### CVE-2026-3854：GitHub RCE via X-Stat Push Option Injection

**测绘对象**：GitHub.com 的 git push → X-Stat header → 内部处理 → hook 执行链

**为什么选它（不选另外两个）**：

| 候选 | 不选的理由 |
|------|-----------|
| curl up 2026 演讲 | 无公开可获取的演讲原文/幻灯片数据，测绘起点不可靠 |
| Nginx→PHP-FPM 编码不一致 | 有技术价值，但与 CVE-2024-4577 在结构上同质（都是编码翻译错误），会重复附录A的模式 |
| **CVE-2026-3854** ✅ | 协议层信任传递错误——和 curl 案例（BDFL/人为中心）完全不同模式 |

**和 curl 案例的差异**：
- curl：信任在**人**之间传递（发现者→安全团队→Daniel）
- CVE-2026-3854：信任在**协议层**传递（git→X-Stat header→内部分析器→hook执行器）
- 差异 = 方法论可复用性的最佳验证点：测绘框架能在完全不同的信任模式上工作

## scanning-checklist.md 验证计划

| checklist项 | CVE-2026-3854 中对应的位置 |
|------------|--------------------------|
| 区块一：系统通过广泛信任的协议暴露非标准功能？ | git push option —— 1996年的git协议，不是安全边界 |
| 区块二：用户输入被拼接进结构化格式？ | push option → `";"` 拼接进 X-Stat header |
| 区块二："最后者胜"重复键解析器？ | 内部分析器取header中每个key的最后出现值 |
| 区块二：外部输入进入内部参数解析器？ | push option → HTTP header → key=value 解析器 → Hook配置覆盖 |
| 区块三：环境模式可被外部输入影响？ | rails_env=staging 通过注入覆盖 sandbox 限制 |
| 区块四：系统支持 hook/plugin？注入钩子？ | pre-receive hooks → custom_hooks_dir → 路径穿越 |

**验证目标**：跑完 scanning-checklist.md 后，能否 100% 覆盖 CVE-2026-3854 攻击链中的所有信任边界？
如果 checklist 全覆盖了测绘对象，说明它在方法论意义上"可用"。如果有遗漏，就是迭代点。

## 信任链初稿

```
git客户端           GitHub接收端          X-Stat 解析器       Hook执行器
┌──────────┐      ┌──────────────┐      ┌──────────────┐      ┌──────────┐
│  用户    │      │ 接收 push    │      │ 解析 header  │      │ 执行钩子 │
│  push    │ ──▶  │ 拼接 X-Stat  │ ──▶  │ 取最后值     │ ──▶  │ 运行脚本 │
│  -o      │      │ ; 分隔       │      │ dict[key]=v  │      │ git用户  │
└──────────┘      └──────────────┘      └──────────────┘      └──────────┘
      │                  │                     │                    │
      │  信任:           │  信任:              │  信任:             │  信任:
      │  -o 只传元数据   │  ; 不在用户输入中   │  key=value 完整    │  hooks路径
      │  不改变行为      │  header 安全        │  按预期解析        │  指向正确脚本
```

**信任关系清单**（初稿）：

| 编号 | 信任方→被信任方 | 信任内容 | 担保形式 | 可验证性 |
|------|----------------|---------|---------|---------|
| T1 | git客户端→git服务端 | push option 只传元数据，不改变执行路径 | 协议设计 | 弱——下游处理链不透明 |
| T2 | 接收端→X-Stat解析器 | header拼接后语义完整，`;`不会出现 | 代码设计 | 弱——无分隔符转义机制 |
| T3 | 解析器→Hook执行器 | 解析出的key=value准确反映输入意图 | 代码设计 | 中——取最后值行为非预期但确定 |
| T4 | Hook执行器→系统 | hook路径指向的是安全的脚本 | 配置信任 | 弱——路径穿越检查不完整 |
| T5 | GitHub→用户 | push option处理是安全的 | 默认假设 | 弱——无外部审计历史 |
