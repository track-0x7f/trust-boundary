# 跨域信任瓦解类型学

> TrustBoundary 方法论的理论层
> 从编码边界到语义边界的信任崩塌模式系统性综合
> v3 — 2026-06-03: 新增"验证-执行顺序倒置"为第6个崩塌模式
> v3 驱动案例: 智能合约预言机(Mango Markets) × AI Agent(Perplexity Comet) 碰撞
> v3 验证CVE: CVE-2023-38545 (SOCKS5) / CVE-2018-7489 (Jackson反序列化)

---

## 核心命题

**信任崩塌不是偶然事件，是特定结构在特定条件下的可预测表现。**

所有被我测绘过的信任边界共享一个底层结构：

> 数据从 System A 传递到 System B 时，A 基于一个**未验证的假设**做出了决策。
> B 的"正确处理"和 A 的预期不一致时，信任崩塌。

---

## 维度一：边界类型

| 边界类型 | 定义 | 测绘过的案例 | 典型案例 |
|:---------|:-----|:------------|:---------|
| **编码边界** | 数据在不同编码/字符集/字节表示之间传递 | CVE-2024-4577、Nginx→FastCGI | 0xAD→0x2D (Best-Fit) |
| **协议边界** | 数据在不同协议/接口规范之间传递 | Nginx→FastCGI、CVE-2026-3854 | FastCGI parameter构造、X-Stat header拼接 |
| **元数据边界** | 结构化数据在跨处理阶段时被选择性降级 | 供应链yanked包、Nginx F2 header静默丢弃 | yanked:true从API→resolver→installer逐级丢失 |
| **语义边界** | 文本在具有不同"理解"的系统之间传递 | Perplexity Comet、提示注入 | LLM无法区分用户指令和网页内容 |
| **人类流程边界** | 信息在不同角色/组织之间传递 | curl信任链、CrowdWorks客服漏斗 | "No bug bounty"声明被新发现者误解 |
| **业务逻辑边界** | 用户输入与应用预期行为之间 | Juice Shop、人人信 | Mass Assignment、SQL注入 |

### 边界轴的连续性

```
编码边界 → 协议边界 → 元数据边界 → 语义边界 → 人类流程边界 → 业务逻辑边界

```

## 维度二：崩塌模式

### 模式A: 翻译错误 (Translation Error)

**结构**：System A 将数据传递给 System B 时，假设 B 会保持数据的语义/身份不变。但 B 在"正确处理"时改变了它。

**四次独立出现（覆盖4个域）：**

| 实例 | 域 | A 的假设 | B 的"正确" | 翻译错误 |
|:-----|:---|:---------|:----------|:---------|
| **CVE-2024-4577** | 编码 | PHP信任0xAD就是0xAD | Best-Fit: 0xAD→0x2D | `%AD` → `-` → RCE |
| **Nginx→FastCGI** | 编码+协议 | Nginx信任字节透传 | PHP接受超长UTF-8 | `%C0%AE`被解码为`.` |
| **Perplexity Comet** | 语义 | 信任LLM能区分指令起源 | LLM视所有文本为同一上下文 | 网页内容→越权操作 |
| **供应链yanked包** | 元数据 | 信任"yanked=已撤回=不可用" | PEP 592: yanked可被解析安装 | yanked标记在传递依赖上丢失 |

---

### 模式B: 善意声明缺口 (Good-faith Statement Gap)

**结构**：系统/角色做出诚实的声明，但该声明在接收端的上下文中被翻译成了设计者未曾预期的含义。

| 实例 | 声明 | 设计者意图 | 接收端理解 |
|:-----|:-----|:----------|:----------|
| **curl** | "No bug bounty" | "别为了钱来报告" | "完全没有赏金机制" |
| **CrowdWorks** | "よくある質問をご確認ください" | 减少重复客服 | 7层漏斗后才有客服入口 |

**不可移植性**：仅人类流程边界。字节和token没有"声明"的概念。

---

### 模式C: 单点疲劳 (Single Point Fatigue)

**结构**：信任集中在单一节点上。该节点的极限决定整条信任链的弹性。

| 实例 | 疲劳节点 | 失效条件 |
|:-----|:--------|:--------|
| **curl** | Daniel Stenberg | 时间预算耗尽 + AI slop上升 |
| **人人信** | 马克（社区运营者） | 被系统透支后退出 |
| **AI对齐** | RLHF安全工程师 | 新颖绕过出现时现有对齐失效 |

**通用规则**：任何"这个节点出问题，整条链就断"的结构，无论节点是人还是系统。

---

### 模式D: 比例变化脆弱性 (Scale Vulnerability)

**结构**：系统设计时假设输入质量分布恒定。当分布变化时，系统在不变资源下疲劳。

| 实例 | 设计假设 | 实际变化 | 失效 |
|:-----|:--------|:--------|:-----|
| **curl** | 有效报告率~75% | AS slop→有效率降至~5% | 时间被无效报告耗尽 |
| **AI输出过滤** | 违规率低且稳定 | 攻击者规模化绕过 | 过滤器更新跟不上 |

---

### 模式E: 盲区继承 (Blind Spot Inheritance)

**结构**：框架的设计假设被使用者继承但未被使用者验证，漏洞出现在继承的假设上。

| 实例 | 框架假设 | 使用者继承未验证 | 崩塌 |
|:-----|:--------|:----------------|:-----|
| **Juice Shop API** | PUT会验证角色和字段 | "admin才能PUT就够了" | Mass Assignment |
| **人人信 f-sign** | 签名保护所有POST | "有f-sign就安全" | registerCom等触发不了 |
| **PHP-CGI** | Apache不会传恶意`-`字符 | PHP团队假设Apache安全 | `%AD`绕过 |

---

### 模式F: 验证-执行顺序倒置 (Validation-Execution Inversion) ← 新模式

**发现过程**：[碰撞记录] 2026-06-03 多Agent跨域碰撞实验。
智能合约预言机报告（Mango Markets: 协议创建价格又验证价格）与 AI Agent报告（Perplexity Comet: LLM处理网页内容后才检查对齐）同时审视时，注意到两个案例共享同一个结构但此前未在任何模式中覆盖。

**结构**：系统设计假设"验证发生在执行之前"（validate → execute），但实际处理顺序是"执行至少部分发生在验证完成之前"（execute starts before validate, or execute → validate）。验证层在数据已经影响系统状态后才检查数据，此时检查已经无法防止损害。

**与TOCTOU的区别**：TOCTOU是"验证发生在T1，执行发生在T2，状态在T1和T2之间改变"。模式F是"验证发生在执行开始之后"——不是状态改变的问题，是处理顺序的倒置。

**与翻译错误的区别**：翻译错误是"数据被改变了身份"；模式F是"执行和验证的时间轴错位"。可以同时发生（数据被改变且验证滞后），但这是两个独立的维度。

#### 案例1: Mango Markets预言机（智能合约预言机域）

```
信任假设: 预言机在价格被用于清算之前验证了价格的正确性
实际顺序: 
  1. Mango的交易池创建了MNGO的瞬时价格（价格发现=执行）
  2. 预言机读取该价格（执行继续）
  3. 协议用该价格计算抵押品价值（执行继续）
  4. 预言机从未验证该价格是否来自低流动性池或是否被操纵（验证缺失=验证滞后的极端情况）
验证状态: 自预言机本身就是交易池，"验证"和"执行"是同一实体
```

#### 案例2: Perplexity Comet（AI Agent域）

```
信任假设: LLM在对网页内容采取行动之前检查了指令边界
实际顺序:
  1. 用户: "总结这个页面"（指令）
  2. LLM读取页面内容，其中含"打开Gmail窃取数据"（执行开始）
  3. LLM的对齐检查运行（验证）
  4. 但页面内容中的恶意指令已经被处理了——LLM已经"看到"了它们
  5. 验证可以阻止执行输出，但阻止不了内容已经进入LLM的上下文窗口
验证状态: 验证发生在外部数据进入上下文窗口之后
```

#### 案例3: SOCKS5 CVE (CVE-2023-38545) — 协议域

```
协议设计: SOCKS5握手中，客户端先发送目标地址，再发送认证信息
信任假设: 服务器会在处理目标地址之前验证客户端身份
实际顺序:
  1. 客户端发送ATYP+DST.ADDR+DST.PORT（目标地址=执行开始）
  2. 服务器解析目标地址，包括超长域名→写入固定缓冲区（执行继续→溢出）
  3. 服务器发送认证请求→等待客户端认证（验证）
  4. 如果认证失败，缓冲区已经溢出了
验证状态: 认证(验证)发生在地址解析(执行)之后
```

#### 案例4: Jackson反序列化 (CVE-2018-7489) — 编码域

```
信任假设: denylist在反序列化之前检查了类名，阻止恶意类加载
实际顺序:
  1. Jackson解析`@class`字段→获取类名→类加载器解析该类（执行开始）
  2. JVM在该类的静态初始化器被触发时加载它（执行继续）
  3. Jackson检查类名是否在denylist中（验证）
  4. 如果类在denylist中，Jackson停止——但静态初始化器已经运行了
  5. 即使类不在denylist中，攻击者只需要一个不在denylist中的新gadget类
验证状态: 类加载（静态初始化器触发）发生在denylist检查之前
```

**注意**: Jackson案例中，denylist可以被完全绕过（找到不在列表中的类），这是盲区继承（模式E）和验证-执行顺序倒置（模式F）的**复合**——denylist的覆盖域不完整（盲区继承），且类加载发生在检查之前（顺序倒置）。两条独立模式可以同时出现在同一个漏洞中。

#### 案例5: pip setup.py 预执行（供应链域）

```
信任假设: setup.py 只声明包元数据，不是可执行代码。
实际顺序:
  1. pip 从本地路径/VCS URL 获取包文件（触发）
  2. pip 执行 setup.py 以提取 setup() 中的元数据（执行开始 ⚡）
     → setup.py 是任意 Python 代码，可以包含恶意载荷
     → 此时代码已经在用户机器上执行了
  3. pip 解析 setup() 声明的依赖（执行继续）
  4. pip 验证包来源/签名/哈希（验证）
     → 如果验证失败，代码已经在步骤2中执行了，来不及阻止
验证状态: setup.py 执行（任意代码执行）发生在来源/签名验证之前
```

**映射到类型学**:
- 翻译错误（R1）: 开发者信任 "setup.py" = "声明式配置"，但 Python 解释器看到的是 "可执行代码"（语义翻译错误）
- 验证-执行倒置（F）: 执行（setup.py）发生在验证（来源检查）之前

**与PEP 767的关系**: 2025 年提议的 wheel 签名标准（PEP 767）要求在 wheel 提取前验证签名。如果正确实现，这是一个“验证→执行”的安全顺序。如果实现不完整（如某些私有注册表跳过签名验证），则是F模式在供应链中的另一个出现点。

#### 模式F的通用定义

**触发条件**: 系统中存在一条路径，其中"执行端"和"验证端"共享同一个数据通道，但执行端在该通道上的数据消费早于验证端的检查。

**验证方法**: 如果一个攻击者可以在验证层"发现"攻击之前就获得攻击效果——且验证层无法回滚该效果——就是模式F。

**与三脉冲的关系**: 三脉冲的探针设计（encode → send → compare response）本身就是执行先于验证——先发送payload，再检查响应。但三脉冲的"验证"是事后的，不影响攻击面。

#### 模式F的独立性边界

模式F在独立出现和与其他模式复合时，利用难度和影响范围有系统性差异：

| 出现形态 | 案例 | 利用难度 | 影响 |
|:---------|:-----|:---------|:-----|
| **F独立** (纯时序问题) | SOCKS5: 地址处理→认证校验 | 需要找到一条执行发生在验证之前的路径 | 初始访问/缓冲区溢出 |
| **F+E复合** (时序+盲区) | Jackson: 类加载→denylist检查 + denylist不完整 | 较低——盲区扩大了可攻击面，时序让攻击在"被阻止"前已生效 | 远程代码执行 |
| **F+R1复合** (时序+翻译) | Perplexity Comet: 页面内容处理→对齐检查 + LLM无法区分指令起源 | 中等——翻译错误创造了攻击入口，时序让对齐来不及阻止 | 数据渗出/越权操作 |
| **F孤立但验证层缺失** | Mango Markets: 无价格验证 | 低——没有验证层就不存在"倒置"问题 | 全系统失陷 |

**关键结论**:

1. **F模式独立致命需要两个条件同时满足**：①执行在验证之前发生；②已有验证层（如果验证层完全缺失，是其他模式）。SOCKS5是唯一满足①且②的纯独立案例。

2. **F模式的真实威力在复合**：它可以放大其他模式的破坏力（E+F，R1+F）。盲区继承让攻击者找到进入路径，验证-执行倒置让攻击在"被阻止"前已经造成损害。

3. **F模式作为独立模式的价值在于诊断风险，而不是预测利用难度**：即使F单独不致命——系统中存在"执行→验证"路径意味着不论验证层多完善，总有一些攻击效果无法被回滚。

## 碰撞实验方法论（可复现的协议）

> 2026-06-03 第一次碰撞实验成功产生了F模式。以下是固化后的可复现协议。

### 碰撞实验的三个必要条件

| 条件 | 定义 | 本次实验的满足情况 |
|:-----|:-----|:-----------------|
| **距离充分性** | 两个领域在底层机制上必须足够不同。编码域（字节变换）和语义域（含义解释）的距离足够；同域的两个不同协议不够。 | ✅ 预言机（经济/密码学信任）vs AI Agent（语义/对齐信任） |
| **结构可映射性** | 双方的核心信任假设在抽象后至少在一个维度上可比较。本次比较的是"验证和执行的时间顺序"。 | ✅ 两者都有"验证层"和"执行层"，但谁先运行不同 |
| **共享术语不存在** | 两个领域没有共用一套技术术语。如果共用（比如"JWT"在前后端都出现），容易产生已知模式匹配而非真正的碰撞。 | ✅ 预言机用"验证者委员会/共识"，AI用"对齐/提示注入"——无共享术语 |

### 碰撞实验的触发条件

不是读完两份报告就开始找相似性——那是模式匹配。
碰撞的触发是：**分别读完报告后，在寻找它们的"共同缺失部分"时产生的不适感。**

本次实验中的触发时刻：读完预言机报告的"Mango Markets自指循环"时，我同时想到了AI报告中的"Perplexity Comet LLM处理内容后才检查"——不是因为它们在结构上相似（那是模式匹配），而是因为它们都让我产生了"验证是不是太晚了"的不适感。那个不适感不属于任何已有模式的描述域。

### 判定标准

- **模式匹配**（已知模式跨域迁移）：碰撞点可以用已有类型学条目（R1-R5）完全解释。指向具体模式。
- **碰撞成功**（新模式产生）：碰撞点无法用任何已有条目解释。它揭示了之前从未独立存在的攻击维度。

### 如果碰撞没有产生新模式——两种可能的解释

| 原因 | 诊断方法 | 应对策略 |
|:-----|:---------|:---------|
| **领域选择不合适**（距离不够/结构不可映射） | 碰撞点在已有模式中有完全或接近完全的解释 | 更换领域，加大距离（如硬件+流程、密码协议+社交工程） |
| **碰撞方法本身有局限**（多次尝试不同领域组合均无新模式） | 3次独立碰撞实验均无新模式产生 | 接受"非所有创新都可训练"，承认碰撞方法的边界：它适用于发现"共同缺失部分"，不适用于发明全新攻击机制 |

### 下次碰撞实验的候选组合

| 组合 | 距离 | 结构可映射性？ | 上次未尝试的理由 |
|:-----|:-----|:--------------|:----------------|
| K8s隔离信任 × 智能合约沙箱 | 大（容器vs区块链） | 两者都有"沙箱隔离"假设，但隔离机制完全不同（Linux namespace vs EVM gas限制） | 新组合，尚未实验 |
| DNS信任链 × 供应链依赖解析 | 中（两个都有"委托授权"结构） | DNS有显式的DS/DNSKEY委托链；供应链的委托是隐式的（版本号解析依赖上游决定） | 有"委托"共性但可能产生已知模式匹配 |

## 预测: 跨链桥中的验证-执行顺序倒置

### 领域: Web3 跨链桥

**候选崩塌位置**: **Fast-path 共识 → 快速最终性**

许多跨链桥（如Wormhole、Multichain、Axelar）使用验证者委员会来验证跨链交易。为了降低延迟，设计了"快速最终性"路径——其中验证者的子集（threshold < full validator set）可以批准一笔交易。

**预测的崩塌条件**:
```
信任假设: 快速最终性路径上的验证者子集和完整验证者集一样安全
实际顺序:
  1. N个验证者中的K个验证了跨链交易（阈值达成 ≈ 执行开始）
  2. 桥合约在链B上铸造了代币（执行完成）
  3. 剩余的N-K个验证者本应验证同一笔交易（验证）
  4. 但代币已经铸造并可以在链B上流通
  5. 如果K个验证者中有恶意节点，验证者验证是一笔假交易
  6. 全体验证者"发现"欺诈时，代币已经在链B上被利用了
```

**这与Mango Markets的结构同构**:
- Mango: 瞬时价格被视为有效（快速验证≈K个验证者）→ 全量验证（完整验证者集）太晚了
- 跨链桥: 快速最终性（K个验证者）→ 全量验证（N-K个验证者）太晚了

**验证方式**: 寻找已发生的跨链桥攻击（如Wormhole $326M被盗、Multichain $1.5B被盗），检查攻击链是否包含"快速最终性→验证滞后"的组件。

**模式覆盖**: 如果该预测成立，验证-执行顺序倒置将覆盖4个域（编码/协议/语义/Web3），确认其跨域通用性。

## 模式复合因果链（新增维度）

### 问题：为什么R1、R5、F总是同时出现？

在Jackson、pip setup.py、Perplexity Comet三个案例中，R1+F同时出现。在Jackson和pip中，R5也同时出现。这不是巧合——是**因果**。

### R1 → F 因果机制

**翻译错误（R1）创造了"合理性外衣"——它让设计者相信数据不需要被验证。这个虚假的信任直接导致了验证-执行顺序倒置（F）。**

以pip为例的设计者思维链：

```
"setup.py是声明式配置" (R1: 翻译错误)
  → "声明式配置不可能有安全风险" (虚假信任)
  → "所以我们可以在验证之前执行它" (F: 顺序倒置)
  → 如果某个setup.py包含恶意代码，它在任何验证之前就已执行
```

### R5 → F 因果机制

**盲区继承（R5）提供了"历史正确性"——它让设计者相信框架的默认行为是安全的。这个继承的信任强化了顺序倒置的合理性。**

以Jackson为例的继承链：

```
"多种JSON解析框架都支持@type动态类加载" (R5: 框架的通用设计方案)
  → "这个功能已经用了很多年" (继承的信任)
  → "所以我们可以在检查denylist之前加载类" (F: 顺序倒置)
  → 攻击者只要找到一个不在denylist中的类就能完全绕过
```

### 因果链类型汇总

| 类型 | 公式 | 描述 | 案例 |
|:-----|:-----|:-----|:-----|
| **独立触发** | R1 → F | 翻译错误创造信任→信任让设计者接受执行在前验证在后 | pip setup.py, Perplexity Comet |
| **继承强化** | R5 → F | 盲区继承提供历史依据→历史让设计者接受不安全的设计顺序 | Jackson, pip多源注册表 |
| **双重锁定** | (R1+R5) → F | 翻译错误+历史继承一起让设计者确信流程安全→顺序倒置被两个独立的合理理由锁定 | Jackson (R1: @class=类型标识, R5: 其他框架也这样), pip (R1: setup.py=配置, R5: setuptools一直这样) |

### 因果链预测方法

当评估一个未测绘的系统时，按以下顺序检查：

```
步骤1: 检查是否存在R1（翻译错误）→ 数据身份是否可能被改变？
步骤2: 如果存在R1, 检查是否存在F（顺序倒置）→ 执行是否发生在验证之前？
步骤3: 如果F存在, 检查是否存在R5（盲区继承）→ 设计者是否继承了不合理的历史假设？
步骤4: 如果R1,R5,F都存在, 这是"双重锁定" → 最高优先级
```

**核心启示**: R1不仅是模式——它是其他模式得以成立的前提条件。修复翻译错误（R1）会自动阻止顺序倒置（F）的出现。这是当前类型学中最强大的干预点。

## 跨链桥预测验证（搜索验证）

### 领域: Web3 LayerZero 跨链桥

2026年5月，LayerZero的Kelp DAO桥被攻击，损失$292M。LayerZero公开承认："We made a mistake by allowing our DVN to act as a 1/1 DVN for high-value transactions."

**因果链分析**:

| 类型学维度 | LayerZero Kelp 桥 | 对应模式 |
|:-----------|:------------------|:---------|
| 信任假设 | "1个DVN验证=足够验证" | R1: 翻译错误（1/1阈值≠实际安全） |
| 继承的框架假设 | "DVN配置灵活=安全灵活" | R5: 盲区继承（灵活性被误解为安全性） |
| 执行时序 | 1个DVN批准→立即执行铸币→后续验证 | F: 顺序倒置（铸币在完整验证前已执行） |
| **因果链** | R1（1个验证者就够了）+ R5（DVN一直这样用）→ F（铸币在完全验证前执行） | **双重锁定** |

**结论**: LayerZero Kelp桥的攻击完全符合类型学的R1+R5→F双重锁定因果链。$292M损失=对预测准确性的实证确认。
